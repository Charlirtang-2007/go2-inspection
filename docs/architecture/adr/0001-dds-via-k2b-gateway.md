# ADR-0001：通过 K2B 网关转发 DDS，而不是前端或 AI机台直连机器狗

- 状态：accepted
- 日期：2026-11-04
- 决策者：Charlirtang
- 相关：`architecture/overview.md`、`environment/k2b-setup.md`

## 背景

项目需要一个能跨网络工作的机器狗巡检系统。机器狗 Go2 X 通过 DDS 通信，默认网段是 `192.168.123.x`，用网线直连最稳定。但实际约束有三条：

1. **演示必须无线**：比赛现场如果狗拖着长网线，移动范围受限，且容易绊倒评委，观感不专业。
2. **前端技术栈没有 DDS 绑定**：前端跑在 Windows 的 Tauri/Rust 环境，官方没有提供适配的 DDS 绑定，前端也不该承担通信中间件的职责。
3. **WiFi 下 DDS 组播不可靠**：如果 AI机台直接用无线网卡连狗，DDS 组播在 WiFi 环境下极不稳定，容易丢包。

结论：需要一个“懂 DDS”的中间件放在狗身边，通过**有线**吃 DDS，再通过 **WiFi** 把控制和视频转发出去。K2B（全志 H618，Ubuntu 22.04 ARM64）就是这个中间件。

## 决策

采用 **前端 - 主控 - 边缘网关 - 机器狗** 四级解耦：

- **K2B 边缘网关**跑 `unitree_sdk2py`，对下走 DDS（网线直连 `eth0`，`192.168.123.x`），对上暴露 HTTP REST + MJPEG 视频流（`wlan0`，`192.168.211.194`）。
- **AI机台**通过 HTTP 调用 K2B 控制狗、拉取视频流，专注检测、录制、通知。
- **前端**只通过 WebSocket/HTTP 与 AI机台通信，不接触 DDS。

K2B 上的 `gateway.py` 负责 DDS 初始化（`ChannelFactoryInitialize(0, "eth0")`）、运动客户端、视频客户端和 HTTP 接口；由 `go2-gateway.service` 开机自启、崩溃自动重启。

## 被否方案

| 方案 | 结论 | 原因 |
| :--- | :--- | :--- |
| **前端直连 DDS** | 否 | Rust/前端硬啃 C++ 版 CycloneDDS，开发周期极长、易内存泄漏；前端职责应止于展示 |
| **纯网络层转发（组播转发 / VXLAN 隧道）** | 否 | 靠 IGMP 代理或 VXLAN 桥接 DDS 组播，配置极复杂；WiFi 物理层易丢包，演示必定卡死 |
| **纯 WebRTC 无线控制** | 否 | 试过。固件版本 ≥1.1.15 需要官方 AES 密钥，拿不到，直接卡死 |
| **ROS2 桥接** | 否 | 没试。为一个 3 万的狗搭一套沉重的 ROS2 节点生态，违背 MVP 原则 |

被否方案的共同点：要么把复杂度推给前端，要么在 WiFi 上硬扛组播，要么引入远超项目需要的生态。K2B 网关是“把 DDS 留在有线侧、把 WiFi 留给 HTTP”的最小折中。

## 后果

### 正面

- **无线自由**：狗可以带着 K2B 在场地内移动，不再受网线约束。
- **职责隔离**：AI机台专注检测/录制/通知，K2B 专注 DDS 与转发，前端专注展示。
- **跨网络**：前端和 AI机台只需在同一局域网，不需要接入狗的 DDS 网段。

### 负面（实际感受到的代价）

| 代价 | 表现 | 缓解 |
| :--- | :--- | :--- |
| **多维护一台设备** | 要给 K2B 配网、配 IP、写 systemd，还要处理双网卡（`eth0` 连狗 / `wlan0` 连 WiFi）的路由冲突 | 见 `environment/k2b-setup.md` 步骤 2 和 5 |
| **单点故障** | K2B 过热死机、掉电或程序卡死，AI机台直接变瞎子，整个系统瘫痪 | `gateway.py` 的 `wait_for_network()` 自检 + `systemd` 的 `Restart=always`；但没有冗余 K2B，这是已知架构约束 |
| **多一跳延迟** | 视频流和指令多经过 K2B 转发，控制指令下发有十几毫秒网络延迟 | 肉眼不明显；相比换来的无线自由，这笔交易划算 |

### 不做的事

- 不引入第二台 K2B 做冗余：当前阶段成本收益不匹配，单点风险用 `Restart=always` 和自检兜底。
- 不把 DDS 封装进前端：职责边界不破，前端永远不碰 DDS。
